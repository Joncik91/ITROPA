# ITROPA lean V2: one guided discovery journey

Status: ADOPTED after plan gate round 1 (section 8). No code built yet. Date: 2026-10-20. Repo: Joncik91/ITROPA, main.

## 0. Ask and scope

Verbatim ask (Jounes, 2026-10-20):
> "Tree and timeline from a researched need are the same. Prior art seems only lightly working showing barely anything and same with chains after analyzing. Maybe the app also wants to do to much. Maybe we need to create a lean V2 with clear guidance, explanation, mobile first with still execution of the end goal and the vision."
> "Read the architecture first because cross-pollination, mechanism extraction, pattern recognition, prior-art analysis, chain analytics, deep dive, app concepts, are part of the discovery process"

Vision (docs/project-overview.md): invert the question, "Given a human need, what industries could emerge to serve it?" End goal (src/types.ts AppConcept, ConstraintsProfile): a buildable app concept that fits the user's skills, time and revenue goal.

Assumptions:
1. "Lean" means fewer screens and clicks, not fewer discovery capabilities. Every capability he named survives, as a step in one guided path.
2. V2 is a new entry beside V1 (`/v2/`), reusing the API layer, the Anthropic provider, the Dexie database and the prompts. V1 keeps working until V2 replaces it.
3. Mobile first: a 390 px wide phone is the primary target; desktop is the same single column, wider.

Not doing:
- Deleting V1. Reason: he has data in it and V2 is unproven; deletion is a later, separate step.
- New AI providers, auth, server-side storage. Reason: out of the ask.
- Changing the data already stored in IndexedDB. Reason: V2 reads the same `needs` table so V1 data opens in V2.

## 3. Non-guarantees and rejected alternatives

- The prior art is the model's recall, not web research; it can be wrong or out of date. Rejected: adding web search now (a larger change, out of the ask).
- No promise V2 output is "better"; check 3 only proves it is not thin.
- Rejected: strip V1 in place. The shared state hooks tie every view together, so leftovers are likely.
- Rejected: keep 15 separate framework calls. They re-summarise the same JSON, which costs 15 calls for overlapping prose (read from `framework-analyzer.ts`; not measured).
- A cut-off AI answer that the JSON repair can still parse is saved as if complete: the API client drops the `truncated` flag and V1's client file is out of scope. Check 7 therefore covers errors and unrepairable JSON only (found in the slice 1 review, 20 Oct 2026).
- Industries are generated once per need and saved. A re-research with a description refreshes prior art and the field read but keeps the saved industries (slice 2 decision).
- Combine keeps only the highest-synergy hybrid of the five the model proposes; the other four are not shown (slice 3 decision, simpler list). Rejected: a chooser of all five.
- Reviewers are told not to raise these.

## 4. Design (each line cites its checks)

The journey, one screen per step, in order, saved per need:
1. **Need**: pick from the standard list or type your own; shows the interpreted core need. [1, 7]
2. **Field**: prior art, all four categories in full (name, mechanism, limitation/lesson), then one "field read" call that merges the five prior-art frameworks into one schema: gaps, white space, who leads, how it evolved, where to enter. [1, 3, F3]
3. **Industries**: one list of future industries with the "inspired by" lineage inline; history eras collapsed above. This replaces both tree and timeline. [2]
4. **Dig in** on an industry (result text shown in full, not headers only): *Understand* (mechanism extraction and deep dive in one call), *Branch* (sub-industries), *Combine* (cross-pollination of two). [6, 6b, 7]
5. **Build**: app concepts for an industry, scored against the saved constraints profile. With no saved profile it uses the default and shows an "Edit profile" form (fields from `ConstraintsProfile`) inline. [5, 5b, 5c]
6. **Insights** (needs 2+ saved needs): cross-need patterns and the inspiration chain, each one call over stored data. [9]

The merged field read is a new prompt (the other prompts are reused as they are). Every step has a "What this is" line, a "Why it matters" line and one primary "Next" button. [4]
New code lives in `src/v2/`, entry `v2/index.html`, added as a second Vite input. It imports `src/services/*`, `src/utils/need-model.ts`, and the Dexie repositories unchanged. [8, 10]
Saving is per call, not per step: prior art and the field read are separate records, each validated by the existing normalisers before it is saved. A failed call saves nothing and shows Retry for that call only; records from earlier calls are kept. [7]
Facts from outside the repo: Anthropic `temperature` is rejected for claude-sonnet-5-5 (observed in service log 2026-10-20 18:36, fixed in a55dfe0). Vite multi-page input via `build.rollupOptions.input`: UNVERIFIED; check 10 fails if wrong.

## 6. Escalate if

Stop and ask if: a V1 stored field must change shape; a new dependency is needed; the field-read output is thinner than five separate calls (check 3 fails twice).
Ask first: new dependencies, Dexie schema bump, Vite or CI config changes.
Never: touch V1 files except `vite.config.ts` input entry; delete or weaken a V1 test; commit `.env`.
House style to copy: `src/components/PriorArtDisplay.tsx` and `src/components/ui/*`.

## 7. Attack on this spec

Easiest break: check 1 passes on a fixture while real output stays hidden. Mitigation: check 3 is a live run, and check 1 must use a fixture saved from that live run.
